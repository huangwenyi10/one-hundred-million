# 多音字读音准确规范（固定规范第 29 条 · 强制）

> 解决问题：TTS（`zh-CN-YunxiNeural`）对中文多音字按上下文猜读，技术语境下频繁读错——典型如「一行代码」的「行」读成 **xíng**（应为 **háng**）。读音错误是观众最直观的硬伤，必须在配音阶段前处理掉，不能等成片出来再返工。
> 使用位置：Step 1（写稿后扫稿）、Step 3（配音前代理 + 配音后核验）、Quality Gates。
> 工具：`scripts/polyphone_check.py` + `scripts/polyphone_dict.json`。

---

## 一、核心机制：同音字代理法

**原理**：把一个会读错的字，在 **TTS 的输入文本**里换成一个**只有唯一读音的同音字**——TTS 必然读对；字幕与画面仍用原稿的原字，观众「听到正确读音、看到正确汉字」。

```
原稿（字幕/画面用）  ：这一行代码
TTS 输入（只读不听）：这一航代码      ← 「行」→「航」，航只有 háng 一个读音
成片效果            ：听到 yī háng dài mǎ，字幕显示「这一行代码」
```

**三条纪律（不可破）**

1. **代理字只进 TTS 输入，绝不进字幕、画面、口播稿交付件**。
2. **还原后必须校验**：`check_sync.py` 的字幕 == 口播稿（原稿）必须成立——代理字若残留在字幕里，校验会失败。
3. **禁用 SSML `<phoneme>` 强制读音**（已实测踩坑）：`zh-CN-YunxiNeural` 下 `<phoneme>` 会让音频体积膨胀 4~5 倍（同句 8s → 36s），总时长彻底失控，不可用。

## 二、三档处置（按词典 `action` 字段执行）

| 档 | 含义 | 处置 | 典型条目 |
|---|---|---|---|
| **A · check** | 已实测 TTS 读对，或 TTS 默认即正确 | **不代理**，仅抽检试听；试听发现读错再临时转代理 | 处理 chǔ、提供 gōng、效率 lǜ、增长 zhǎng、命中 zhòng、响应 yìng、重写 chóng、调整 tiáo、执行 xíng、系统 xì |
| **B · proxy** | 已确认会读错 / 高风险未验证 | **必须代理**（正确性优先于韵律自然度） | 一行 háng、更新 gēng、加载 zài、调用 diào、为了 wèi、还原 huán、尽管 jǐn、差异 chā、间隔 jiàn、粘贴 zhān、卷 juàn |
| **C · 改写规避** | 无稳妥同音代理字（同音字极罕见） | **改写口播表述**，绕开这个字 | 「卡顿」qiǎ（IT 口语普遍读 kǎ，无同音字）→ 改说「不流畅 / 阻塞」；「重载 overload」chóng/zhòng 两读并存 → 改说「重新加载 / 过载」 |

## 三、标准 SOP（Step 1 → Step 3，不可跳过）

```bash
PY=/Users/ay/.workbuddy/binaries/python/envs/default/bin/python
D=/Users/ay/.workbuddy/skills/one-hundred-million/scripts

# ① Step 1 写稿后：扫稿列出所有多音字命中
$PY $D/polyphone_check.py scan "<标题>_口播稿.txt"
#    输出【需代理】/【抽检】两类；--strict 可在有需代理项时 exit 1 作门禁

# ② Step 3 配音前：生成 TTS 输入版（替换代理字）+ 映射文件
$PY $D/polyphone_check.py apply "<标题>_口播稿.txt" \
      --out build/script_tts.txt --map build/polyphone_map.json

# ③ 用 build/script_tts.txt（不是原稿）跑分段 TTS
#    → build/segments_durations.json（真实时间轴）+ build/voiceover.mp3 + build/subtitles.srt

# ④ 配音后：把字幕里的代理字换回原字（这一步漏了，字幕就会出现「一航代码」）
$PY $D/polyphone_check.py restore --srt build/subtitles.srt \
      --map build/polyphone_map.json --out build/subtitles_fixed.srt

# ⑤ 用还原后的字幕交付，并跑四方同频校验
$PY $D/check_sync.py build/segments_durations.json build/subtitles_fixed.srt \
      "<标题>_口播稿.txt" build/voiceover.mp3
```

**关键约束**：时间轴（⑤ 的 durations）来自真实音频，**字幕文本来自原稿**——两者合起来才既「读音正确」又「字幕==口播稿」。第 ④ 步是整个流程最容易漏的一环。

**代理字冲突**：若原稿本身已含某个代理字（如「在」），脚本会自动切到备选（如「再」）；主选与备选全冲突时**跳过该条并告警**——绝不强行替换，否则第 ④ 步会把原稿里本来就有的字误换掉。

## 五、2026-09-05 实测记录（edge-tts 7.2.8 + ffmpeg，音色 zh-CN-YunxiNeural）

方法：合成音频 → ffmpeg 解 16k/单声道 PCM → 归一化 → 归一化互相关（corr）比对波形。

1. **TTS 输出非字节确定**：同一文本合成两次，MP3 的 MD5 不同、PCM 也有微小抖动（第一次整句级 rmse≈125）。→ **不能靠 MD5 做缓存命中或一致性比对**；时长一律以真实音频为准。
2. **孤立重复单字法 100% 确定**（如「行行行」，corr=1.000），可判定 TTS 的**默认读音**：
   - 孤立「行」→ 与「形形形」波形**完全一致**（corr=1.000）→ 默认读 **xíng**；与「航航航」不同（corr≈0）。**这就是「一行代码」被读成 xíng 的根因**。
   - 孤立「处」→ 与「触触触」一致（corr=1.000）→ 默认读 **chù**；但词级「处理」实测读 **chǔ**（正确），说明 TTS 有词级词典覆盖。
3. **词级实测读对（A 档）**：处理 chǔ、提供 gōng、效率 lǜ、增长 zhǎng、命中 zhòng、响应 yìng、重写 chóng（三连重复法 corr>0.9）；调整 tiáo（单词法 corr=1.000）。
4. **方法学边界（诚实记录）**：把词里的字替换成代理字后（如「更新」→「耕新」），生造词会改变整体韵律，波形比对失效（corr 接近 0），**无法据此自动判定对错**。故「更新 / 加载 / 调用」等判为**未验证**，按正确性优先一律走 B 档代理——宁可韵律略生硬，不可读音错误。
5. **未来自证方法**：遇到新可疑字，用「孤立重复单字法」测其默认读音（corr=1.000 级判定），与期望读音比对即可确认是否需要代理；结论补录进 `polyphone_dict.json`。

## 六、词典维护（技能自我进化）

- 词典 = `scripts/polyphone_dict.json`，字段：`char / want / wrong / contexts[] / proxy / proxy_alt[] / action / note`。
- **发现新的读错案例 → 就地补录**：加一条 entry（`action=proxy`），并挑一个**唯一读音**的代理字 + 1~2 个备选；确认读对的补 `action=check`。
- **代理字选取标准**：①只有唯一读音（排除「琢」zhuó/zuó、「叉」chā/chá 这类多读字）；②常用字，TTS 字库必认（生僻字可能读不出）；③尽量不常用，降低与原稿撞字的概率。
- 每 10 期复盘时，把实际踩到的错读案例批量回灌词典。
